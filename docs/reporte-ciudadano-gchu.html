App de Reporte Ciudadano

Gualeguaychú — una app para que el vecino reporte baches, luminarias, basura y otros problemas de la vía pública en cinco pasos, y para que el municipio los reciba, asigne a cuadrilla y resuelva con trazabilidad completa.

Resumen del proyecto

contexto

La app corre sobre Expo SDK 54 y habla con la API hermana api-reporte-ciudadano (Compose). Del lado del vecino, el flujo de reporte es de cinco pasos con foto obligatoria, GPS, texto o voz, adhesión a duplicados cercanos, cola offline en SQLite y push al cambiar el estado. Del lado del operador, la bandeja filtra y asigna; el detalle cambia estado, marca duplicado, corrige zona y sube la foto del arreglo; también se puede escanear el QR. El invitado mira el mapa público sin cuenta. Las zonas se consultan, no se administran. Abajo: pantallas, componentes, estructura y contrato con la API.

Por qué existe esta app. Hoy el Centro de Atención al Vecino carga todo a mano en una planilla compartida. El trimestre pasado cargaron catorce veces el mismo bache por llamadas repetidas, una rama mal anotada tardó tres semanas en atenderse y cortó la luz de media manzana, y el intendente se enteró de un pozo por Facebook en vez de por el propio equipo. La detección de duplicados a 50 m, el número de seguimiento y los avisos automáticos existen puntualmente para que esas tres cosas no vuelvan a pasar.
"El vecino no se enoja porque el bache tarde. Se enoja porque nadie le dice nada."— Claudia Benítez, Centro de Atención al Vecino de Gualeguaychú
Sin sesión / invitado — el mapa se mira sin cuenta. El vecino se identifica en register (también sirve para reingresar); el operador entra por login.

  • Botón "Grabar nota de voz" vía expo-audio
  • Timer de grabación en pantalla
  • Reproducción de la nota antes de enviar

Paso 5 — Confirmación

  • Preview de la foto tomada
  • Tipo de problema seleccionado
  • Ubicación en un mapa pequeño
  • Descripción o nota de voz adjunta
  • Zona calculada con el pin (zonaParaCoordenadas). No usa la zona del usuario
  • Si el pin cae fuera de los cuatro polígonos, queda en Zona Centro
  • Botón "Enviar reporte"

Pantalla 10

Detalle de gestión

src/app/(operador)/reporte/[id].tsx

Información visible

  • Código, estado, tipo, dirección y zona
  • Autor, cantidad de fotos y, si hay cuadrilla, su nombre
  • Foto del problema y, si existe, la foto del arreglo
  • Si es duplicado, el código del reporte original
  • Historial de cambios, con el comentario (incluye eventos de zona corregida)

Acciones, cada una en su sheet

  • Cambiar estado (SheetEstado): comentario obligatorio. Si el estado nuevo es resuelto, la foto del arreglo también
  • Marcar duplicado (SheetDuplicado): elige otro reporte que no sea ya un duplicado
  • Asignar (SheetAsignar): solo cuadrillas activas de la zona del reporte
  • Corregir zona (SheetZona): si el pin cayó en la zona equivocada
  • Un reporte resuelto, rechazado o ya marcado como duplicado no se vuelve a gestionar
Pantalla 11

Zonas y cuadrillas

src/app/(operador)/zonas.tsx
  • Las cuatro zonas se listan siempre. La del operador se marca "Tu zona" y no se ocultan las demás
  • Cada tarjeta muestra nombre, referente y "N cuadrillas"
  • Debajo, cada cuadrilla con su nombre, especialidad y un chip Activa / Inactiva. El chip se lee, no se toca
  • Zona Este, sin cuadrillas: "Todavía no hay cuadrillas en esta zona."
  • El operador no da de alta ni de baja zonas ni cuadrillas. El pedido no lo incluye, y Zona no tiene un campo de estado
  • La zona del reporte sale del pin al crearlo, no de esta pantalla. El filtro por zona está en la bandeja

Fuera de esta versión

scope

Cosas que Claudia pidió dejar afuera de la primera entrega. Escritas acá para no sumarlas "de paso" y correr la fecha sin darnos cuenta.

  • Turnos, trámites y pagos municipales — esto es solo reclamos
  • Chat entre el vecino y el operador — alcanza con los cambios de estado con comentario
  • Estadísticas y tableros para las secretarías
  • Integración con el sistema de expedientes de la Municipalidad
  • Encuesta de satisfacción al cerrar el reclamo
  • Alta y baja de zonas o cuadrillas. El operador las consulta; no las crea ni las activa o desactiva

Reglas no negociables

cruzan todas las pantallas

No son de una pantalla puntual — aplican en toda la app y son las que Claudia remarcó como no negociables.

  • Sin foto no hay reporte. Si el vecino no da permiso de cámara, la app se lo explica con buenos modos y le ofrece abrir la configuración del sistema — no lo deja trabado sin salida.
  • Si niega la ubicación, tiene que poder reportar igual poniendo el punto a mano en el mapa.
  • Buena parte de quienes reclaman tiene más de 60 años: letra grande, botones grandes, y la nota de voz como alternativa real a escribir, no un agregado menor.
  • El mapa público muestra el reporte, nunca quién lo hizo.
  • Sin señal la app anda igual: el reporte se guarda en el teléfono con sincronizado: false y se sube solo al volver la conexión, sin que el vecino tenga que acordarse de nada.
  • Crear un reporte tiene que poder hacerse parado en la vereda, en menos de un minuto.

Contrato de API y convenciones

api-reporte-ciudadano

Forma real de las respuestas. La app apunta con EXPO_PUBLIC_API_URL / _EMULADOR / _TELEFONO. En tests (NODE_ENV=test) los servicios siguen usando mocks.

// éxito { "datos": [ ... ], "meta": { "total": 128, "pagina": 1, "porPagina": 20 } } // error { "error": { "codigo": "FOTO_REQUERIDA", "mensaje": "El reporte necesita al menos una foto." } }
idsSiempre cadenas de texto, nunca números.
fechasTexto ISO 8601 con zona ("2026-09-14T10:22:00-03:00"). Nunca un objeto Date ni un número.
clavesSiempre en camelCase.
valores ausentesUn campo sin valor viene como null — nunca ausente, nunca cadena vacía.
sesiónAuthorization: Bearer <token> vía Axios. Token en expo-secure-store, nunca en kv-store.
pushPOST /dispositivos con el Expo Push Token; DELETE al cerrar. Avisos al autor si avisosActivos.
fotos APILa API manda fotos con momento problema|arreglo; la app las separa en fotos[] y fotoArreglo.

Estrategia de mocks y servicios

src/mocks/ · src/servicios/

La API real ya está cableada. Los mocks siguen vivos para Jest y para catálogos de apoyo en UI.

  • Los tipos viven en src/tipos/ y son el contrato compartido con la API
  • Los datos de demo/test van en src/mocks/, tipados contra esos mismos tipos
  • Las pantallas no hablan con Axios directo: pasan por src/servicios/ (api.ts, auth.ts, reportes.ts, bandeja.ts, zonas.ts, cuadrillas.ts, notificaciones.ts, ubicacion.ts, mapa.ts, base-datos.ts…)
  • enPrueba() hace que en Jest se usen mocks; en la app se llama a la API
  • Los mocks de test cubren los casos feos: sin audio, rechazado con motivo largo, lista vacía, varios cambios de estado, error de red / sin conexión
